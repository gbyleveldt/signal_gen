## System Clock: 122.88MHz

The system clock is set to 122.88MHz in `main.c` via `set_sys_clock_khz(122880, false)`.

This is not an arbitrary value. The RP2040 has no hardware I2S peripheral — I2S is generated by a PIO state machine. The PIO clock divider must be an integer (or very close to it) to avoid BCK jitter that would cause downstream I2S devices to mislock.

For 48kHz stereo 32-bit I2S:
- BCK = 3.072MHz (sample_rate × 64)
- PIO clock = BCK × 2 = 6.144MHz
- Divider = 122,880,000 / 6,144,000 = **20 exactly**

The `false` argument to `set_sys_clock_khz` means the firmware will not panic if the PLL cannot achieve the exact value — it falls back gracefully. At the fallback of 125MHz the divider becomes 20.345 (fractional), introducing ~1.7% BCK jitter. This is acceptable for the PCM5102A which has an internal PLL, but worth knowing if a strict I2S slave is connected downstream.

## DMA Ping-Pong: The `start=false` Bug

The DMA IRQ handler in `src/i2s/i2s.c` repoints the completed channel with `start=false`:

```c
dma_channel_set_read_addr(done_ch, _bufs.buf[done_buf], false);
```

**Do not change this to `start=true`.** This was the original implementation and it caused a serious bug.

**What the bug looked like:** Harsh noise at approximately 100Hz with a periodic tick approximately once per second.

**Why it happened:** With `chain_to` configured (ch_a chains to ch_b, ch_b chains to ch_a), the hardware handles channel handoff automatically. Calling `start=true` in the IRQ handler immediately started the completed channel — while the other channel was still running. Both channels were feeding the PIO TX FIFO simultaneously, corrupting the audio stream. The ~100Hz noise corresponded to the buffer-rate frequency; the ~1s tick was a PIO FIFO underrun/resync cycle.

**Why `start=false` is correct:** The `chain_to` mechanism starts the next channel the moment the current one completes. The IRQ handler only needs to refill the buffer and repoint the channel for the *next* time it runs. There is no need to manually start anything.

See `components/i2s-pio-rp2040.md` in `gbyleveldt/claude-skills` for the full PIO I2S pattern documentation.

## Dual-Core Split

- **Core 0:** Audio engine — DMA IRQ fill callback, `tight_loop_contents()` in `audio_engine_run()`
- **Core 1:** UI — LVGL tick and task handler, encoder polling, display flush

**Why this split:** The DMA IRQ handler on Core 0 is timing-critical. It must complete within a bounded window to refill the audio buffer before the next DMA transfer completes (~5.3ms at 256-pair buffers, 48kHz). LVGL's `lv_task_handler()` takes variable time depending on dirty region size and SPI flush latency. Placing both on the same core risks LVGL blocking the audio IRQ long enough to cause a buffer underrun.

**Do not move LVGL operations to Core 0.** The timing margin is sufficient but not generous.

**Cross-core shared state** (`freq_hz`, `amplitude`, `channel`) is protected by a Pico SDK `spin_lock_t`. The audio engine takes a single snapshot per buffer fill (~188Hz rate) rather than locking per-sample — overhead at this rate is negligible.

## Encoder Driver: Struct-Based Multi-Instance Design

The encoder driver (`src/encoder/`) uses a struct-based design with a shared GPIO IRQ dispatcher rather than static module-level state.

**Why:** This project requires two encoders (frequency and amplitude). A single-instance design using static variables cannot support this — a second call to `gpio_set_irq_enabled_with_callback()` would silently overwrite the first callback, causing one encoder's interrupts to be handled by the wrong logic.

The struct-based design registers one shared IRQ callback that dispatches to the correct `encoder_t` instance based on which GPIO fired. Each instance is initialised via `encoder_init(&enc, pin_a, pin_b, pin_pb)` and carries its own state independently.

**The button debounce fix:** The original implementation applied the 150ms debounce gate to both FALL (press) and RISE (release) edges using a single `last_pb_time` timestamp. If a button press was shorter than 150ms, the RISE event failed the gate and was discarded — `pb_state` was never cleared and `pb_event` never fired, breaking subsequent presses unpredictably. The fix applies debounce only to FALL, and always processes RISE if a valid press (`pb_state == true`) is on record.

## Hardware Constraints: GP17–GP25 Unusable

On the Waveshare RP2040-Zero, **GP17–GP25 are exposed as underside pads only** — they are not castellated and cannot be used with standard through-hole breakout pins. All peripherals are constrained to GP0–GP15 and GP26–GP29.

This has two visible consequences in the codebase:

**Display on SPI1 (not SPI0):** The natural SPI0 MOSI/SCK pins (GP19, GP18) fall in the unusable range. The display is therefore wired to SPI1 on GP26 (SCK) and GP27 (MOSI). All `spi1` references in the display driver are a direct consequence of this constraint, not a preference.

**No onboard LED:** GP25 is the onboard LED on the official Pico. It does not exist on the Zero — GP16 is the WS2812 RGB LED instead. There is no status LED in this codebase.

For display-specific gotchas (LV_COLOR_16_SWAP, 34px Y offset, MADCTL for landscape orientation), see `components/st7789.md` in `gbyleveldt/claude-skills` — these are fully documented there and apply to this project as-is.

## Si5351A: Reserved but Unpopulated

I2C1 pins GP14 (SDA) and GP15 (SCL) are defined in `config.h` and wired on the PCB, but the Si5351A clock generator IC is not populated.

**Why they are reserved:** The RP2040 cannot synthesise a clean 12.288MHz MCLK directly from its 12MHz XOSC (no exact integer divisor). A future DSP slave project will require this signal as a reference clock. The Si5351A solves this via its configurable PLL, generating phase-coherent clocks from a single reference — including 12.288MHz MCLK, and optionally BCK and LRCK.

**What a future maintainer needs to do:** Populate the Si5351A breakout, implement the I2C driver, and configure CLK0 for 12.288MHz output. The synchronisation strategy should be decided at that time — either the Si5351 generates all three I2S clocks (with PIO running in slave mode) or it generates MCLK only (with PIO dividing BCK/LRCK from the MCLK input). See `components/pcm5102.md` in `gbyleveldt/claude-skills` for the full discussion.

## LVGL v8.3 (Not v9)

LVGL v8.3 is used via git submodule (`lib/lvgl`). v9 was evaluated before this project started.

**Why v8.3:** At the time of development, the RP2040 + Pico SDK integration path for v9 was thinner — fewer community examples and no equivalent of ESP-IDF's `esp_lvgl_port`. The v9 API changes (opaque handle-based registration replacing the struct-based pattern) would have added integration uncertainty on a constrained target. v8.3 has a well-understood, battle-tested API for bare-metal embedded use.

**Known build quirk:** `LV_BUILD_EXAMPLES OFF` is not honoured by v8.3's CMake — examples and demos are always built regardless. They must be manually commented out in `lib/lvgl/env_support/cmake/custom.cmake`. See `components/lvgl.md` in `gbyleveldt/claude-skills` for the exact lines to comment out.

## Channel Cycling Feature

The amplitude encoder button cycles output routing: `ALL → LEFT → RIGHT → MUTE → ALL`.

This feature was added reactively during hardware testing, not planned from the start. Its first use immediately revealed that the 3.5mm-to-RCA adapter cable had its Left and Right channels reversed — routing to a single channel made a wiring fault that would otherwise have been tedious to isolate into a 30-second diagnosis.

It serves as a diagnostic tool as much as a user feature. Retain it for that reason, even if it seems like unnecessary complexity for a simple signal generator.
